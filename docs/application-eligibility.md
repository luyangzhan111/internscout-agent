# 投递条件判断

本功能属于当前工作区 Stage 15，尚未发布新版本。[开发任务与验收标准](tasks/stage-15-application-eligibility.md)。

Stage 16 已将同一套条件检查用于 [Agent 推荐](agent-recommendations.md)，可同时查看技能覆盖、资格排序和原文依据；本页仍可独立检查当前页岗位。

当前资格版本为`stage23-rules-v1`。学历层级与在读/已取得分别比较；学历分支能力说明保留原文提醒，本岗混合/远程工作形式用于细化城市检查。真正的任选、放宽、冲突及无效证据仍保守。有限支持“2028届及以后”这类明确边界；复杂毕业日期仍可能待确认。[本轮任务与验收](tasks/stage-23-education-work-location.md)。

## 使用流程

1. 启动项目后，在页面顶部选择 **投递条件**。
2. 填写自己确定的信息：毕业届次、学历与在读／已取得状态、正式工作经验月数、可接受城市和可实习月数。不确定的项目留空。经验填 `0` 表示无正式工作经验；城市选择不限表示愿意接受任意城市。
3. 选择岗位来源、招聘状态和页码，点击判断按钮。每次只判断当前页（最多 20 条），不是整个岗位库。
4. 展开岗位，查看五项结果及对应原文；对“待确认”的内容，可回到原岗位或向招聘方核实。
5. 修改自己的条件、换页或更新岗位后，重新判断。页面交互会重新读取岗位；外部更新不会主动推送到已经打开且没有交互的页面。

上述步骤不需要模型或 embedding 密钥，也不产生模型费用。候选人填写的信息仅用于本次请求和浏览器会话，不写入数据库。岗位库、导入和更新流程见 [使用说明](job-imports.md)。

## 如何理解结果

| 结果 | 含义 |
| --- | --- |
| 符合 | 已识别的明确条件与填写信息相符，或岗位明确写了该项不限。 |
| 不符合 | 有明确硬条件与填写信息冲突；已关闭岗位另列阻断原因。 |
| 待确认 | 岗位没写、候选人未填、条件仅为偏好、表述含糊或冲突，或超出首版支持范围。 |

总评只要有一项明确不符合就是“不符合”；否则只要还有待确认就是“待确认”；五项都符合才显示“符合”。这是条件检查，不是录用预测，也不是原有技能匹配分数。

Stage 17 将待确认原因分类展示，并给出下一步建议：

| 原因类型 | 含义与下一步 |
| --- | --- |
| 个人信息缺失 | 已有可比较的岗位条件，但个人字段或学历状态未填写；先补充相应信息。 |
| 原文未说明 | 原文没有可比较的硬条件，或只写了偏好；需要核对完整岗位或询问招聘方。 |
| 无法可靠判断 | 存在含糊表达、系统不支持的比较或无效证据；需要人工核对，不能由模型猜测补全。 |
| 要求冲突 | 同一维度存在相互矛盾的要求；需要招聘方澄清。 |

分类按当前阻止判断的原因提供：如果原文尚无条件，即使个人信息也未填，仍先说明原文缺失。填写完整资料不会自动消除岗位信息的不确定性。旧会话缺少分类字段时只保留原理由，不猜测分类。

“硕士优先”“能实习六个月更佳”等偏好会单独解释，不作为硬性拒绝条件。当前版本按有限规则识别届次、学历、时间长度和城市，不用模型猜测未写出的要求。学历的在读／已取得有区别，特定领域经验不能直接等同于任意工作月数；精确毕业日期、每周到岗天数、技能、专业和其他要求仍需阅读原文。

可实习月数按能提供的连续时长填写。低于明确最低要求可判不符合；超过岗位期限的上界则待确认，需核实能否按岗位期限安排。正式工作经验的明确上下界按月数直接比较。

岗位内容使用库中最新保存的快照；判断过程不会自动刷新招聘网站。原文依据来自岗位标题、描述或城市字段，随返回结果提供精确字符位置，支持核对与追溯。

## API

`POST /api/eligibility/evaluate`

以下是虚构测试档案，仅用于说明格式：

```json
{
  "job_ids": [7, 8],
  "profile": {
    "graduation_year": 2027,
    "degree": "bachelor",
    "degree_status": "enrolled",
    "work_experience_months": 0,
    "acceptable_cities": ["北京", "深圳"],
    "internship_months": 6
  }
}
```

所有 profile 字段均可省略或为 `null`；城市 `[]` 表示明确不限。`degree` 支持 `below_associate / associate / bachelor / master / doctor`，状态支持 `enrolled / completed`。

一次 1–50 个不重复的正整数岗位 ID；非法输入返回 422，任一 ID 不存在则整个请求返回 404。返回 `items` 和 UTC `assessed_at`；每项包括当前岗位、五项 `checks`、总评 `overall`、阻断原因、原文内容指纹和规则版本。状态值为 `met / not_met / unknown`。每段 `evidence` 包含 `field / text / start / end`，满足 `job[field][start:end] == text`（Python 字符索引，不是 UTF-16 索引）。

每项检查新增 `unknown_reason`（`candidate_missing / source_unspecified / interpretation_uncertain / requirements_conflict`）和 `next_step`。新规则对未知状态提供分类及中文建议，已确定的状态不携带未知原因。旧构造允许 `null`／空字符串以兼容既有客户端和缓存。

本轮不提供长期个人档案、不自动提交申请，也不把待确认岗位排除出岗位库。规则测试与真实快照检查用于开发验收，不代表对所有招聘写法的识别准确率。

## Stage22 学历范围

Stage22历史版本为`stage22-rules-v1`。“研究生”保留硕士、博士集合；明确的本科/研究生并列、研究生/博士生在读、硕博在读及共同状态不再只取一个学历。指定“硕士研究生”仍保留该指定层级；状态只适用于部分分支或含替代身份、连读、冲突、否定/偏好时继续待确认，导师/协作对象不当申请人门槛。

当时留出发现的学生称谓、按学历分组能力及更高学历接受口径问题是Stage23的开发输入，详见[Stage22分析](evaluations/stage22-analysis.md)。

## Stage23 学历分支与工作地点

“招募本科生、硕士研究生”属于申请人集合并约束在读；后续“本科生需具备项目能力”“硕士研究经验优先”属于相应分支能力，不作为全体申请人的第二个学历门槛。内部`ConditionRule.degree_scope`区分`applicant`与`conditional_capability`，`degree_exclusive`记录明确排他；HTTP五维检查格式不变。界面原文依据及备注会保留分支要求，系统没有据此认证项目能力。

高于原文列出的学历、但原文没有明确接受/排除时保持待确认；明确排他、上下限和独立在读状态仍严格核对。混合取得/在读、跨维任选及作用域不清保持待确认，不能推测以前已取得的学位。

城市检查识别的是本岗位的办公/实习形式。混合或远程但允许异地的范围不明时，不再仅按办公城市硬拒异地候选，而是提示核实地域、到岗频次；意向城市匹配或明确不限时只认定地理维度满足，并保留出勤/搬迁/工作许可尚未验证的提醒。明确必须到岗、不支持异地、远程限定城市仍按硬要求比较；全远程本身不代表全球可工作。真正互相矛盾的要求待确认，明确可选地点按可选范围判断。

组织线上线下活动、远程团队、历史远程经验、系统部署等不改变城市判断；没有本岗形式信号时返回原城市检查。所有依据来自当前岗位快照的精确字符范围，关闭岗位仍阻断。规则只覆盖有限表达，未识别的复杂分支和地理范围仍需招聘方确认。
